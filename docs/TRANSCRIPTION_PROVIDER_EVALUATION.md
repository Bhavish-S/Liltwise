# Transcription provider evaluation — Milestone 5B-0

Research checked on **2026-10-12** against the official documentation linked below. Pricing and model availability change; recheck before implementation. This document compares documented interfaces and engineering costs. It contains no recorded speech, performance benchmark, or accuracy claim.

## What the current matcher accepts

`AdaptiveSpeakingSession.apply` accepts one Zod-validated control at a time. A transcript control is `{ type: "transcript", text, isFinal, timestampMs?, providerConfidence? }`; controls also include pause, resume, stop, and explicit resynchronization.

- `text` is the complete current utterance/recognition hypothesis (up to 2,000 characters), not an incremental delta. Each interim can replace the previous preview. Only a final can confirm progress.
- `timestampMs`, if present, is compared to the last accepted timestamp and older values are ignored. There is no session ID, provider event ID, segment/item ID, revision number, or deduplication key. A timestamp is not presently a source-of-truth global ordering mechanism.
- `providerConfidence` is optional. It gates a match only when supplied. The result's `confidence` is the engine's lexical match score; it is not a provider score and is not calibrated as a probability. The matcher does not invent a provider confidence or timestamp.
- Pause is an explicit control; the matcher does not detect silence or infer that a talk has ended. Resume and stop are also explicit. Repeated divergence can request manual recovery, and resynchronization requires a script section/token position.
- Matching is bounded, mostly near-verbatim word matching. It is not semantic paraphrase recognition. The exact original section text remains the displayed source.

The automated synthetic suite in `packages/domain/src/transcription-fixtures.ts` covers exact words; punctuation/case; contractions/recognition errors; filler; pause/resume; skip; repeated locations; interim corrections; stale events; improvisation/digressions; transitions; Kannada/Unicode; specialist names; mixed English/Kannada; empty/low-information/malformed input. These cases validate deterministic matcher behavior only. They are not ASR accuracy results.

### Evidence, estimates, and unknowns

**Documented facts:** event names and delta/final payload distinction, `item_id` ordering caveat, language hints, delay levels, missing live confidence/timestamps, and current published price are in OpenAI's current official guide and model/pricing pages. The listed OS platforms, sample streaming approaches, hardware backends, and project license facts come from the upstream project READMEs. Apple and Microsoft platform/runtime facts come from their official developer docs.

**Engineering estimates:** a cloud adapter is likely the least native integration work for this Electron product, but it adds recurring API cost and network dependence. Local engines reduce routine audio transmission but add model/native packaging and device resource work. Platform-native engines multiply maintenance across independent code paths.

**Unverified:** comparative latency, match error, battery/CPU/memory, Kannada and code-switch recognition quality, preferred model size, Electron mic permission UX, app signing/notarization, network resilience, and privacy/retention interpretations for production. No benchmark was run in this milestone.

## Recommended adapter contract (design only)

Do not send provider wire events directly into the matcher. Use an adapter that converts each provider's event stream to a normalized application event such as:

```ts
type TranscriptEvent = {
  sessionId: string;
  eventId: string;
  segmentId: string;       // OpenAI item_id maps here
  revision: number;
  status: 'interim' | 'final';
  text: string;            // complete current segment, never a raw delta
  sourceTimeMs?: number;   // only if provider actually supplies it
  receivedAtMs: number;    // local monotonic clock, not speech time
  language?: string;       // only if supplied/detected
  providerConfidence?: number; // only if provider supplies it
};
```

The adapter accumulates OpenAI delta strings by item, replaces interim text with the provider's final `transcript`, and orders finalized items using provider identity/order where possible. It must not fabricate word timestamps, confidence, language, or a stable result. The domain matcher should receive a complete segment text as `text`, `status === 'final'` as `isFinal`, and optional provider confidence. A follow-up contract milestone should add event/session identity and safe deduplication before live wiring; current `timestampMs` alone cannot reconcile delayed/replayed provider events.

Provider lifecycle is separate from transcript text: `connecting`, `listening`, `paused`, `stopped`, recoverable `error`, and terminal `closed` states should be surfaced to the UI. Pause must stop or suspend capture and clear buffered audio as supported; stop/disconnect must stop media tracks, close sockets/peer connections, cancel pending work, and dispose listeners. Only request microphone permission after explicit user action. Show a persistent listening indicator and a stop control. Default to no audio recording and no transcript retention. Capture only the selected presenter microphone, never system/meeting loopback. Tell the user before audio leaves their device and identify the service. Keep the provider unable to access arbitrary IPC/window controls.

## Recommended first real provider

Prototype OpenAI `gpt-live-transcribe` behind the normalized provider interface as the first **opt-in benchmark candidate**, not as a final exclusive product decision. It has a documented transcription-only real-time path, client-side short-lived credentials, delta/final events, tunable delay, context/keyword/language hints, and a simple usage price. This reduces first implementation complexity while validating whether local CPU/native integration is needed. Reject or defer it if consented user tests show unacceptable network dependency, Kannada performance, or per-minute cost. Keep a local/offline comparison based on `whisper.cpp` as the second candidate; choose only after the same real samples and target computers are tested.

## Future real-device benchmark protocol

1. Recruit speakers who explicitly consent to microphone capture for this evaluation. Use scripted, non-confidential samples: English, Kannada, code-switching, varied accents, names/product terms, natural pauses, repetitions, skips, improvisation, interruptions, and controlled room noise.
2. Record one reference set with consent, store it encrypted in a restricted test location, assign pseudonymous participant IDs, and set a short deletion date. Delete raw audio after comparison unless participants separately consent to longer retention. Do not collect meeting/system audio.
3. Replay the exact same capture files through each provider and repeat live microphone trials. Record provider/model/version, OS/device, settings, network, and timestamps. Do not tune one provider on test utterances and report that as an unbiased comparison.
4. Measure speech-to-first-usable-text and speech-to-stable-final latency; word/character transcript error; alignment token/section error; unnecessary forward/backward jumps; recovery time after skips; terminology handling; empty/truncated outputs; CPU, peak memory, network bytes, and battery/power impact.
5. Report per-language and per-condition distributions, not only averages. Keep provider recognition confidence and Liltwise match confidence as separate fields. Repeat on supported macOS Apple Silicon and representative Windows x64 devices before shipping both platforms.
